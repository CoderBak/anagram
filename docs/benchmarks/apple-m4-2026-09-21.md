# EditLens inference on Apple M4

Measured September 21, 2026 on Apple M4, 10 CPU cores, 24 GiB unified memory, macOS 27.2. These are local engineering measurements of the existing four-class RoBERTa-large classifier, not a detector-accuracy study. Original weights and the installed component were not modified.

The model is [Pangram's EditLens RoBERTa-large](https://huggingface.co/pangram/editlens_roberta-large), redistributed with attribution and CC BY-NC-SA 4.0 in the [Anagram modelkit](https://huggingface.co/CoderBak/editlens_roberta_modelkit). Source and variant hashes are recorded in the accompanying JSON; this benchmark does not change model licensing.

## Method

- Each configuration ran in a fresh process, sequentially: three warmups and 20 measured batches. Latency includes input transfer, synchronized inference and returning four CPU logits. Cleaning/tokenization, language detection, transport and browser work are excluded.
- The same cleaned English browser-fixture paragraphs and concatenated passages were tokenized once per worker, right-padded to 128 or 512 tokens and EOS-preserving truncated. These synthetic fixture texts are not a labeled evaluation corpus. Input hashes match across implementations.
- MPS used Torch SDPA with CPU fallback disabled. MLX reused the installed `mlx-embeddings` XLM-RoBERTa encoder unchanged and loaded the original four-class dense → tanh → output head. Strict loading required mapping 98 legacy LayerNorm `gamma`/`beta` names to `weight`/`bias`; the failed first attempt is retained in the raw reports. Position padding was checked separately.
- The MLX encoder materializes explicit attention and uses FP32 softmax, while Torch uses SDPA. Results compare these particular implementations, not the maximum performance of either framework. A future fused MLX attention experiment should be separate.
- ORT CoreML used MLProgram, static input shape overrides and `ALL` compute units. Profiling verified actual CoreML partitions alongside CPU operations; it does not establish ANE-only execution. FP32/FP16 CoreML labels describe the ONNX graph, not guaranteed internal hardware arithmetic. Profiling ended before timed samples.
- CoreML cold/cache sessions used the same per-case model cache. “Cold” means no experiment model cache; the OS file cache was not flushed. Conversion, compilation and load cannot be separated through this ORT session interface, so their combined time is reported.
- RSS is sampled every 50 ms in the worker, including the shared Transformers tokenizer/import stack. It is not the minimum deployable footprint of each framework. Device memory counters overlap unified RAM and must not be added to RSS. CoreML service allocations may be absent from client RSS.
- Cases ran in deterministic order without controlled cooldown or thermal/power measurements. Twenty samples describe this run; they do not establish confidence intervals or stable rankings across machines.

Versions: Python 3.13.0; Torch 2.14.0; Transformers 5.17.0; ONNX Runtime 1.30.0; MLX/MLX Metal 0.32.2; mlx-embeddings 0.1.0. CoreMLTools 9.0 was available but direct conversion was unnecessary because the ORT provider worked. The GPL-3.0 MLX dependency is experimental and is not packaged in the product.

## Memory and practical implications

The following are **worker RSS observations**, not total model or physical-memory usage. This example uses 8 × 512 (the cached session for CoreML):

| Implementation | Baseline RSS | Loaded RSS | Sampled measurement peak RSS |
| --- | ---: | ---: | ---: |
| MPS FP32 | 42.2 MiB | 410.6 MiB | 532.7 MiB |
| MPS FP16 | 40.8 MiB | 935.8 MiB | 1055.2 MiB |
| MLX FP32 | 40.9 MiB | 1752.9 MiB | 1761.1 MiB |
| MLX FP16 | 41.5 MiB | 1213.9 MiB | 1220.9 MiB |
| COREML FP32 | 41.5 MiB | 2027.7 MiB | 2499.7 MiB |
| COREML FP16 | 42.3 MiB | 773.3 MiB | 874.3 MiB |

For the repeated MPS FP32 8 × 512 reference, measured RSS fell from **532.7 MiB to 231.1 MiB while MPS active and driver counters stayed identical**. FP16 also showed higher worker RSS than FP32 while its MPS active allocations were about half as large. Therefore these RSS values cannot establish that FP16 uses more physical memory, or that MLX consumes more total RAM than MPS. Paging, mapped/shared allocations and runtime ownership affect what RSS counts; this experiment did not attribute the change to a specific OS mechanism.

Separate device counters for 8 × 512 (maximum observed after each measured batch):

| Implementation | Counter | Bytes expressed as GiB |
| --- | --- | ---: |
| MPS FP32 | active | 1.327 |
| MPS FP32 | driver | 2.040 |
| MPS FP16 | active | 0.664 |
| MPS FP16 | driver | 1.008 |
| MLX FP32 | active | 1.324 |
| MLX FP32 | allocator_peak | 2.511 |
| MLX FP32 | cache | 1.203 |
| MLX FP16 | active | 0.662 |
| MLX FP16 | allocator_peak | 1.404 |
| MLX FP16 | cache | 1.526 |

Full counter ranges and RSS observations remain per case in JSON. MPS driver memory includes cache; MLX active, cache and allocator-peak counters have different scopes. Do not add them to RSS or combine them into a cross-runtime total-memory ranking. CoreML exposes no comparable device counter here, and its service allocations may be missing from client RSS.

CoreML FP16 showed promising short-text latency, while its compilation and cached startup costs are substantial. These static-shape tests also require a production design for shape buckets, cache size and eviction before adoption. MLX was competitive on short single inputs but slower in the longer/batched configurations of this particular encoder. These observations justify a focused CoreML startup/cache investigation and, separately, a fused-attention MLX experiment; they do not justify silently changing the production runtime or precision.

## Reproduce and inspect

Run with the existing modelkit and isolated experimental dependencies; `--check` imports dependencies without loading checkpoint weights. The script creates fresh experiment directories and deletes only their generated caches unless `--keep-cache` is requested.

```sh
python scripts/benchmark-apple.py --check
python scripts/benchmark-apple.py --run --batches 1 --lengths 128
python scripts/benchmark-apple.py --run --backends mps mlx --batches 1 --lengths 512
python scripts/benchmark-apple.py --run --backends mps mlx --batches 8 --lengths 128 512
python scripts/benchmark-apple.py --run --backends coreml --batches 8 --lengths 512 --timeout 480
```

Use `--model-dir`, `--deps` and `--output` to override local paths. The script automatically measures an MPS FP32 reference for each requested shape. CoreML 8 × 512 uses an eight-minute worker limit; a failed cold session skips its warm retry.

The [complete JSON](apple-m4-2026-09-21.json) contains exact metrics, logits, input/model/fixture fingerprints, versions, repeat references, failures and cache cleanup records. [Raw run JSON and warmup profiles](experimental/apple-m4-2026-09-21/) preserve the experiment with home paths replaced by `$WORKSPACE`/`$HOME`.

Implementation sources: [benchmark script](../../scripts/benchmark-apple.py), [ORT CoreML provider](https://onnxruntime.ai/docs/execution-providers/CoreML-ExecutionProvider.html), [mlx-embeddings](https://github.com/Blaizzy/mlx-embeddings), [MLX memory accounting](https://ml-explore.github.io/mlx/build/html/python/memory_management.html).
